# REST API Overview

## 1. Status and URL

This document describes the contract actually exposed by the initial FastAPI backend. It does not promise prospective routes. The specification generated by FastAPI remains the executable reference:

- default application prefix: `/api`;
- interactive documentation: `/docs`;
- OpenAPI schema: `/openapi.json`;
- health check, outside the prefix: `GET /health` → `{"status": "ok"}`.

The prefix can be changed with `API_PREFIX`, but Angular and the tests must use the same value.

## 2. Common conventions

### 2.1 Transport and formats

- request and response bodies use JSON;
- properties use `snake_case`;
- numeric identifiers are generated by SQL Server;
- date/time values use ISO 8601 and represent UTC values;
- all `/api` routes use `Authorization: Bearer <jwt>` authentication except `/api/auth/login`;
- an absent optional value is represented by `null`;
- the human-readable ticket reference follows `TKT-YYYYMMDD-8HEX`, for example `TKT-20260816-A1B2C3D4`.

The main controlled values are:

```text
Role:             ADMIN | MANAGER | AGENT | CLIENT
Priority:         LOW | MEDIUM | HIGH | CRITICAL
TicketStatus:     NEW | ASSIGNED | IN_PROGRESS | WAITING |
                  RESOLVED | VALIDATED | CLOSED | REOPENED
TaskStatus:       TODO | IN_PROGRESS | BLOCKED | DONE | CANCELLED
NotificationType: ASSIGNMENT | SLA_WARNING | SLA_OVERDUE |
                  TASK_WARNING | TASK_OVERDUE | UPDATE
SlaStatus:        NOT_CONFIGURED | ON_TRACK | OVERDUE | MET | BREACHED
```

An approaching deadline produces an `SLA_WARNING` notification; it does not create an additional SLA status.

### 2.2 List responses

Only the main ticket list is paginated in the MVP:

```json
{
  "items": [],
  "total": 0,
  "page": 1,
  "page_size": 20
}
```

Users, customers, catalog items, tasks, comments, events, and notifications are returned as simple JSON arrays. Any limit parameters are documented for the relevant endpoint.

### 2.3 Errors

A business error follows the current FastAPI format:

```json
{
  "detail": "Transition from CLOSED to IN_PROGRESS is not allowed"
}
```

A Pydantic validation error returns `422` with FastAPI's standard `detail` array. The main status codes are:

| Code | Meaning |
|---:|---|
| `200` | successful read, command, or update |
| `201` | successful creation |
| `400` | invalid business value, including an incorrect current password |
| `401` | invalid/expired credentials or JWT |
| `403` | insufficient role or scope |
| `404` | resource absent or not visible to the user |
| `409` | duplicate or operation incompatible with the current state |
| `422` | invalid body, parameter, or related reference |

An out-of-scope ticket returns `404`, which avoids revealing its existence.

## 3. Authentication

### `POST /api/auth/login`

Public route.

```json
{
  "email": "agent@example.com",
  "password": "example-password"
}
```

`200` response:

```json
{
  "access_token": "<jwt>",
  "token_type": "bearer"
}
```

An unknown email address, an incorrect password, or an inactive account returns the same `401`. The JWT contains `sub`, `iat`, and `exp`; its default lifetime is 60 minutes.

### `GET /api/auth/me`

Returns the active user loaded from the database: `id`, `first_name`, `last_name`, `email`, `role`, `customer_id`, `is_active`, `created_at`, and `updated_at`.

### `POST /api/auth/change-password`

```json
{
  "current_password": "current-password",
  "new_password": "new-password"
}
```

The new password must contain at least 8 characters. The response is `{"message": "Password changed successfully"}`.

There is no `/logout` route in this MVP: Angular logs out by removing the local token. There is also no server-side JWT refresh or revocation.

## 4. Ticket visibility rules

Ticket, task, comment, history, and dashboard routes reuse the same scope:

| Role | Visible tickets |
|---|---|
| `ADMIN` | all |
| `MANAGER` | all |
| `AGENT` | tickets whose `assigned_user_id` matches the agent's identifier |
| `CLIENT` | tickets created by that account for its linked `customer_id` |

A query filter can never broaden this scope.

## 5. Users

| Method and route | Access | Parameters/body |
|---|---|---|
| `GET /api/users` | ADMIN, MANAGER | `search`, `role`, `active_only=true` |
| `POST /api/users` | ADMIN | creation |
| `GET /api/users/{user_id}` | ADMIN, MANAGER | none |
| `PATCH /api/users/{user_id}` | ADMIN | supplied fields only |

Creation:

```json
{
  "first_name": "Sara",
  "last_name": "Amrani",
  "email": "sara.amrani@example.com",
  "password": "initial-password",
  "role": "AGENT",
  "customer_id": null,
  "is_active": true
}
```

Rules:

- the email address is normalized to lowercase and must be unique;
- `customer_id` is required for `CLIENT` and forbidden for an internal role;
- the password is hashed and never appears in the response;
- `PATCH` accepts `first_name`, `last_name`, `email`, `role`, `customer_id`, and `is_active`;
- an administrator cannot deactivate their own account through this route.

Response:

```json
{
  "id": 12,
  "first_name": "Sara",
  "last_name": "Amrani",
  "email": "sara.amrani@example.com",
  "role": "AGENT",
  "customer_id": null,
  "is_active": true,
  "created_at": "2026-08-16T09:30:00Z",
  "updated_at": "2026-08-16T09:30:00Z"
}
```

## 6. Customers

| Method and route | Access | Parameters/body |
|---|---|---|
| `GET /api/customers` | any authenticated account | `search`, `active_only=true` |
| `POST /api/customers` | ADMIN, MANAGER | creation |
| `GET /api/customers/{customer_id}` | any authenticated account within its scope | none |
| `PATCH /api/customers/{customer_id}` | ADMIN, MANAGER | update/deactivation |

A `CLIENT` receives only its linked company. `search` applies to `company_name`, `contact_name`, and `email`.

Creation body:

```json
{
  "company_name": "Atlas Demo SARL",
  "contact_name": "Nadia Alami",
  "email": "contact@example.com",
  "phone": "+212600000000",
  "address": "Casablanca"
}
```

Creation sets `is_active=true`. `PATCH` also accepts `is_active`. Deactivation preserves tickets and historical links.

## 7. Catalog and SLA

Catalog read operations are available to any authenticated user. Write operations are restricted to `ADMIN`. A `CLIENT` is always limited to active products, modules, and categories even if `active_only=false` is supplied. The small catalogs return non-paginated arrays.

### Products

| Method and route | Contract |
|---|---|
| `GET /api/catalog/products` | parameter `active_only=true` |
| `POST /api/catalog/products` | `name`, `description?`; `201` response |
| `PATCH /api/catalog/products/{product_id}` | `name?`, `description?`, `is_active?` |

### Modules

| Method and route | Contract |
|---|---|
| `GET /api/catalog/modules` | `product_id?`, `active_only=true` |
| `POST /api/catalog/modules` | `product_id`, `name`, `description?`; `201` response |
| `PATCH /api/catalog/modules/{module_id}` | `name?`, `description?`, `is_active?` |

A module belongs to one product. The ticket stores `module_id`; the product is obtained through the module relationship. Active-only reads and ticket validation require both the module and its parent product to be active.

### Categories

| Method and route | Contract |
|---|---|
| `GET /api/catalog/categories` | parameter `active_only=true` |
| `POST /api/catalog/categories` | `name`, `description?`; `201` response |
| `PATCH /api/catalog/categories/{category_id}` | `name?`, `description?`, `is_active?` |

### SLA

| Method and route | Access |
|---|---|
| `GET /api/catalog/sla` | ADMIN, MANAGER, AGENT |
| `PUT /api/catalog/sla/{priority}` | ADMIN |

`PUT` body:

```json
{
  "target_hours": 16,
  "warning_threshold_percent": 80,
  "is_active": true
}
```

`target_hours` is between 1 and 8760. The threshold is between 1 and 100 and represents the percentage of the target duration elapsed before the alert. The route creates the configuration for that priority if it does not exist; otherwise, it replaces it.

Changing a configuration does not retroactively recalculate existing tickets. Creation without an active configuration remains possible but produces `sla_deadline=null` and `sla_status=NOT_CONFIGURED`.

## 8. Tickets

### 8.1 Paginated search

### `GET /api/tickets`

Parameters:

| Parameter | Values |
|---|---|
| `search` | partial search on reference and subject, maximum 150 characters |
| `customer_id` | exact identifier |
| `status` | a `TicketStatus` |
| `priority` | a `Priority` |
| `category_id` | exact identifier |
| `product_id` | filter by product through the module |
| `module_id` | exact identifier |
| `assigned_user_id` | exact identifier |
| `created_from`, `created_to` | inclusive ISO 8601 bounds |
| `sla_status` | `NOT_CONFIGURED`, `ON_TRACK`, `OVERDUE`, `MET`, or `BREACHED` |
| `sort_by` | `reference`, `created_at`, `updated_at`, `sla_deadline`, or `priority` |
| `sort_direction` | `asc` or `desc`, default `desc` |
| `page`, `page_size` | defaults 1 and 20; maximum 100 per page |

Response: `items`, `total`, `page`, and `page_size`. Each item uses the `TicketRead` schema described below.

### 8.2 Creation

### `POST /api/tickets`

Any active account can call this route.

```json
{
  "customer_id": 5,
  "subject": "Error when opening the company file",
  "description": "A sufficiently precise description of the reported problem.",
  "category_id": 2,
  "module_id": 8,
  "priority": "HIGH"
}
```

- `module_id` is optional; the product is derived from the module;
- the customer and category must be active; a supplied module must be active;
- for `CLIENT`, the backend uses the customer linked to the account and forces the initial priority to `MEDIUM`;
- the backend sets `status=NEW`, the creator, and the timestamps;
- it generates a concurrency-safe reference such as `TKT-20260816-A1B2C3D4`;
- it calculates the deadline with the active configuration, then creates `TICKET_CREATED` in the history;
- the response is `201`.

### 8.3 Read and detail schemas

The base `TicketRead` schema contains:

```json
{
  "id": 41,
  "reference": "TKT-20260816-A1B2C3D4",
  "customer_id": 5,
  "subject": "Error when opening the company file",
  "description": "A sufficiently precise description of the reported problem.",
  "category_id": 2,
  "module_id": 8,
  "priority": "HIGH",
  "status": "IN_PROGRESS",
  "creator_id": 20,
  "assigned_user_id": 12,
  "assigned_user_name": "Sara Amrani",
  "resolution_summary": null,
  "sla_deadline": "2026-08-17T01:30:00Z",
  "sla_status": "ON_TRACK",
  "sla_remaining_minutes": 540,
  "resolved_at": null,
  "validated_at": null,
  "closed_at": null,
  "created_at": "2026-08-16T09:30:00Z",
  "updated_at": "2026-08-16T10:00:00Z"
}
```

`GET /api/tickets/{ticket_id}` returns this schema enriched with three arrays: `tasks`, `comments`, and `history`. For `CLIENT`, `tasks` is always an empty array because tasks are internal. The three resources also have separate routes.

### 8.4 Main-data update

### `PATCH /api/tickets/{ticket_id}`

Partial body:

```json
{
  "subject": "Corrected subject",
  "description": "Corrected description",
  "category_id": 3,
  "module_id": 9
}
```

`ADMIN` and `MANAGER` can update a visible ticket; an `AGENT` must be assigned to it. Statuses `RESOLVED`, `VALIDATED`, and `CLOSED` block this update. Priority, customer, assignment, and status use separate commands.

### 8.5 Assignment

### `POST /api/tickets/{ticket_id}/assign`

Restricted to `ADMIN` and `MANAGER`.

```json
{"assigned_user_id": 12}
```

The target user must be an active `AGENT` or `MANAGER`. The first assignment automatically changes `NEW` to `ASSIGNED`. An assignment creates the `TICKET_ASSIGNED` history event and an `ASSIGNMENT` notification. A `VALIDATED` or `CLOSED` ticket cannot be assigned.

### 8.6 Priority

### `POST /api/tickets/{ticket_id}/priority`

Restricted to `ADMIN` and `MANAGER`.

```json
{"priority": "CRITICAL"}
```

The new deadline is recalculated from the beginning of the current SLA cycle. `PRIORITY_CHANGED` records the old/new priority and deadline. Tickets already `RESOLVED`, `VALIDATED`, or `CLOSED` are locked against retroactive priority changes.

### 8.7 Status and workflow

### `POST /api/tickets/{ticket_id}/status`

```json
{
  "status": "RESOLVED",
  "resolution_summary": "Configuration corrected and opening test passed.",
  "note": "Required reason for transitions that need justification."
}
```

`resolution_summary` is required only for a transition to `RESOLVED`. A non-blank `note` is mandatory for these transitions:

- `IN_PROGRESS → WAITING`;
- `RESOLVED → IN_PROGRESS` (resolution rejection);
- `CLOSED → REOPENED`.

The note is limited to 2,000 characters and is stored in the corresponding ticket-history event. Other transitions may omit it.

Accepted transitions:

| From | To |
|---|---|
| `NEW` | `ASSIGNED` |
| `ASSIGNED` | `IN_PROGRESS` |
| `IN_PROGRESS` | `WAITING`, `RESOLVED` |
| `WAITING` | `IN_PROGRESS` |
| `RESOLVED` | `VALIDATED`, `IN_PROGRESS` |
| `VALIDATED` | `CLOSED` |
| `CLOSED` | `REOPENED` |
| `REOPENED` | `IN_PROGRESS` |

Agents must be assigned to the ticket and can target only `IN_PROGRESS`, `WAITING`, or `RESOLVED`. `VALIDATED`, `CLOSED`, and `REOPENED` are therefore manager/administrator actions. Every transition into `IN_PROGRESS` also checks that the ticket has an active assignee; otherwise it returns `409`.

Timestamp effects:

- `RESOLVED` sets `resolution_summary` and `resolved_at`;
- a `RESOLVED → IN_PROGRESS` rejection clears the current `resolved_at`;
- `VALIDATED` sets `validated_at`;
- `CLOSED` sets `closed_at`, but is rejected with `409` while any ticket task is neither `DONE` nor `CANCELLED`;
- `REOPENED` clears all three terminal timestamps, recalculates the SLA from reopening, and keeps the previous values in the history.

The previous assignee is retained on reopening. A manager can change it while the ticket is `REOPENED`; resuming work is allowed only when the resulting assignee is active.

There is no ticket-deletion route.

## 9. Comments and history

### Comments

| Method and route | Contract |
|---|---|
| `GET /api/tickets/{ticket_id}/comments` | chronological array |
| `POST /api/tickets/{ticket_id}/comments` | body `{"content": "..."}`, `201` response |

Any user with access to the ticket can read and add a comment. Comments are immutable through the API, and every comment follows ticket visibility; there is not yet a distinction between “internal note” and “client comment.”

Response: `id`, `ticket_id`, `author_id`, safe `author_name`, `content`, `created_at`. Creation also adds `COMMENT_ADDED` to the history.

### History

`GET /api/tickets/{ticket_id}/history` returns a read-only chronological array:

```json
{
  "id": 122,
  "ticket_id": 41,
  "actor_id": 12,
  "event_type": "STATUS_IN_PROGRESS",
  "details": "{\"from\": \"ASSIGNED\", \"to\": \"IN_PROGRESS\"}",
  "created_at": "2026-08-16T10:00:00Z"
}
```

`details` is currently a string containing a small serialized JSON object. No endpoint allows the frontend to create, update, or delete an event.

## 10. Tasks

Tasks are internal: the routes below return `403` to `CLIENT`.

| Method and route | Contract |
|---|---|
| `GET /api/tickets/{ticket_id}/tasks` | chronological array |
| `POST /api/tickets/{ticket_id}/tasks` | creates a task, `201` response |
| `PATCH /api/tasks/{task_id}` | updates supplied fields, including status |

Creation:

```json
{
  "title": "Reproduce the incident",
  "description": "Test with a synthetic demonstration file.",
  "assigned_user_id": 12,
  "due_date": "2026-08-16T16:00:00Z"
}
```

Response: `id`, `ticket_id`, `title`, `description`, `assigned_user_id`, safe `assigned_user_name`, `status`, `due_date`, `completed_at`, `created_at`, `updated_at`.

A task starts at `TODO`. `PATCH` accepts `title`, `description`, `assigned_user_id`, `due_date`, `status`, and `note`. The transitions are:

```text
TODO        -> IN_PROGRESS | CANCELLED
IN_PROGRESS -> BLOCKED | DONE | CANCELLED
BLOCKED     -> IN_PROGRESS | CANCELLED
DONE        -> (terminal)
CANCELLED   -> (terminal)
```

An update to `DONE` sets `completed_at`. A transition to `BLOCKED` or `CANCELLED` requires a non-blank `note` of at most 2,000 characters; that note is recorded in ticket history rather than stored as a mutable task field. An `AGENT` cannot cancel a task. An agent can assign a task only to themself, while a manager or administrator can select an active `AGENT` or `MANAGER`.

An agent can update only a task assigned to that same agent on the agent's current ticket. Managers and administrators can update non-terminal tasks on visible non-closed tickets. Reassignment creates history and an in-app notification for the new assignee. A non-null due date must be in the future when created or changed. Terminal tasks and tasks on a closed ticket are immutable. There is no deletion or standalone read-detail endpoint.

Example blocked-task update:

```json
{
  "status": "BLOCKED",
  "note": "Waiting for the customer to provide test access."
}
```

## 11. Notifications

The routes expose only the current user's notifications.

| Method and route | Contract |
|---|---|
| `GET /api/notifications` | `unread_only=false`, `limit=50` between 1 and 200 |
| `GET /api/notifications/unread-count` | `{"count": 3}` |
| `POST /api/notifications/{notification_id}/read` | returns the updated notification |
| `POST /api/notifications/read-all` | returns a confirmation message |

Notification response:

```json
{
  "id": 301,
  "recipient_id": 12,
  "ticket_id": 41,
  "type": "ASSIGNMENT",
  "title": "Ticket assigned",
  "message": "Ticket TKT-20260816-A1B2C3D4 has been assigned to you.",
  "is_read": false,
  "created_at": "2026-08-16T09:45:00Z"
}
```

Both read routes refresh SLA and task alerts first. Duplicates are prevented by recipient, ticket, type, and title. This read-time refresh is not a continuous scheduler: no alert is created in the background when nobody calls these routes.

## 12. Dashboard

### `GET /api/dashboard/summary`

The MVP exposes no filter. Data respects the scope described in section 4.

```json
{
  "total_tickets": 120,
  "open_tickets": 70,
  "in_progress_tickets": 19,
  "resolved_tickets": 22,
  "closed_tickets": 50,
  "overdue_tickets": 7,
  "sla_compliance_rate": 91.3,
  "average_resolution_hours": 12.7,
  "by_status": [{"label": "IN_PROGRESS", "count": 19}],
  "by_priority": [{"label": "HIGH", "count": 28}],
  "by_category": [{"label": "Functional incident", "count": 31}],
  "by_customer": [{"label": "Atlas Demo SARL", "count": 14}],
  "by_assignee": [{"label": "Sara Amrani", "count": 9}]
}
```

- `open_tickets = total_tickets - closed_tickets`;
- `overdue_tickets` counts unresolved tickets whose deadline has passed;
- `average_resolution_hours` measures the current SLA-cycle start to `resolved_at` and is `null` without observations;
- `sla_compliance_rate` measures the proportion resolved before or at the deadline and is `null` without measurable tickets.
- `by_assignee` counts non-closed tickets as the simple workload measure.

Detailed unfinished-task workload, average time since the first `IN_PROGRESS`, and period filters require future endpoints or fields; they are not presented as already available.

## 13. Main API workflow

A complete scenario uses the routes in this order:

1. `POST /api/auth/login`;
2. `GET /api/customers`, `/api/catalog/categories`, `/api/catalog/products`, and `/api/catalog/modules?product_id=...`;
3. `POST /api/tickets`;
4. `POST /api/tickets/{id}/assign`;
5. `POST /api/tickets/{id}/status` to `IN_PROGRESS`;
6. `POST /api/tickets/{id}/tasks`, then `PATCH /api/tasks/{task_id}` to `DONE`;
7. `POST /api/tickets/{id}/comments`;
8. ticket transitions to `RESOLVED`, `VALIDATED`, then `CLOSED`;
9. `GET /api/tickets/{id}/history`;
10. `GET /api/dashboard/summary` and `GET /api/notifications`.

The examples use synthetic data only.

## 14. Explicit limitations of the initial contract

The following are not currently exposed: logout endpoint, refresh token, administrative password reset, attachments, physical deletion, separate internal comments, general pagination, export, email, SLA configuration by customer/product, business calendar, continuous alert scheduling, or advanced analytical dashboard.

Any evolution must first update the FastAPI schemas and routes and their tests, followed by this document and the Angular integration.
